## Motivation

The charm.land ecosystem that AGY itself depends on standardizes on
`github.com/charmbracelet/x/exp/golden` for snapshot-style assertions.
The package's main API (`golden.RequireEqual(t, actual)`) reads the
expected payload from `testdata/<TestName>.golden`, supports a
`-update` flag to regenerate the file, and on mismatch prints a unified
diff (via `aymanbagabas/go-udiff`) — which is dramatically friendlier
than `bytes.Equal`'s either/or error message.

Wagyu had 4 test files that used `bytes.Equal` to compare expected
strings/payloads against actual output:

- `internal/builtinsubagent/image_generator_test.go` — magic-byte
  check + determinism round-trip, both runtime comparisons
- `internal/clipboard/paste_test.go` — small-PNG passthrough identity
  check
- `internal/imagery/imagery_test.go` — five "input equals scaled
  output" identity checks
- `internal/tools/webm_test.go` — two "expected payload equals
  actual return bytes" snapshot tests

After a careful pass, the only two files with genuinely
snapshot-shaped comparisons (an inlined expected payload vs. an actual
function return value) are the ones we migrated:

| File | Tests migrated | Why |
|---|---|---|
| `internal/tools/webm_test.go` | `TestReadFile_WebM_Valid`, `TestReadFile_NonWebMExtension_WebMMagic_NoRejection` | both have an inlined 11-byte WebM payload and a single `bytes.Equal([]byte(got), data)` against the actual `ReadFile` return value — the canonical "expected vs actual" snapshot shape |
| `internal/imagery/imagery_test.go` | `TestScale_PNG_SmallUnchanged` | the input is a deterministic 64×48 solid-red PNG generated by `makeSolidPNG`; comparing `bytes.Equal(data, out)` after `ScaleIfOversized` is functionally "this solid PNG is the golden output of the small-passthrough branch", which is what golden files are for |

The other 2 files were left alone because their `bytes.Equal` calls
are identity comparisons of two in-test-generated inputs (not "literal
expected" vs. "computed actual"):

- `image_generator_test.go:95` compares the first 8 bytes of a
  freshly-generated PNG against the `pngMagic` constant declared in
  the same file — putting a hardcoded 8-byte literal into a separate
  golden file buys nothing.
- `image_generator_test.go:136` is a determinism check (two calls →
  same bytes) — there is no expected literal to extract.
- `clipboard/paste_test.go:117` and the four `imagery_test.go` sites
  on lines 191/240 (now removed)/284/305/336 are all
  `bytes.Equal(input, output)` where the "expected" is itself
  generated in the test body via `makeSolidPNG`/`makeSolidJPEG` (or
  is the raw text "hello, world" / an empty input). Migrating one of
  those is fine (as we did for `TestScale_PNG_SmallUnchanged`); the
  others would be cosmetic churn with no readability win — golden
  files for an in-test-generated blob whose contents are pinned by the
  call right above it.

So: 2 files, 3 tests, 3 golden files. Six `bytes.Equal` sites remain
in the tree across the four files; they were all identity checks where
the golden pattern would have been cosmetic noise rather than an
improvement.

## Golden file generation

```bash
cd internal/tools && \
  go test -update -run 'TestReadFile_WebM_Valid|TestReadFile_NonWebMExtension_WebMMagic_NoRejection' .
# → PASS, writes testdata/TestReadFile_*.golden (11 + 7 bytes)

cd ../imagery && \
  go test -update -run 'TestScale_PNG_SmallUnchanged' .
# → PASS, writes testdata/TestScale_PNG_SmallUnchanged.golden (126 bytes)

# Re-run without -update: golden files match → green.
```

## Behaviour change

None. Same assertions, same outputs.

- `bytes.Equal([]byte(got), data)` vs. `golden.RequireEqual(t, []byte(got))` against
  `testdata/TestReadFile_*.golden`: the binary contents of the
  golden file are byte-identical to the literal `data` slice in the
  test (verified: `11 B` and `7 B` files contain exactly the 11 / 7
  bytes the tests previously hardcoded). Behaviour equivalence by
  construction.
- `bytes.Equal(data, out)` vs. `golden.RequireEqual(t, out)`: same
  semantic — the golden file captures the deterministic PNG output of
  `png.Encode` on a 64×48 solid-red raster. `png.Encode` is
  deterministic, so every run produces the same bytes; the golden file
  is a snapshot of that stable output.

The user-visible difference on failure is significant:

- `bytes.Equal` mismatch: `ReadFile: got 1a45dfa38201021f..., want 1a45dfa38201021f...`
- `golden.RequireEqual` mismatch: `output does not match, expected: …,
  got: …, diff: --- golden … +++ run …`

And the workflow improvement:

```bash
go test -update ./internal/tools/    # regenerate after an intentional change
go test ./internal/tools/            # verify the regenerated golden matches
```

## AGY alignment

- `github.com/charmbracelet/x/exp/golden v0.1.0` is now a **direct
  dep** of the wagyu clone. Prior to this cycle it was in the indirect
  dependency tree (pulled by `charmbracelet/x/exp/slice v0.0.0-20250327172914-2fdc97757edf`,
  but the two packages are independent — `slice` stays indirect, only
  `golden` was promoted).
- The migration surface is small (3 tests, 2 files) because the wagyu
  test suite never accumulated the long-inline-string-expected-output
  patterns that charm.land's own projects use heavily. Future cycles
  that grow TUI snapshot coverage — e.g. ANSI-rendered output, status
  line panels — have the golden-file pattern ready to use.

## Hard constraints / limitations

【硬约束 / 存疑】

- The other 2 candidate files mentioned in the brief
  (`image_generator_test.go` and `paste_test.go`) are deliberately
  NOT migrated. Their `bytes.Equal` sites are runtime identity
  comparisons, not snapshot tests; converting them would replace one
  `bytes.Equal` call with one `golden.RequireEqual` call against an
  externally-stored copy of an in-test-generated payload — net noise,
  no readability gain. The cycle report's "Motivation" table enumerates
  the eight remaining `bytes.Equal` sites and explains why each was
  left alone.
- The three golden files contain raw byte payloads (no `.txt` or
  extension beyond `.golden`), matching the upstream convention
  shipped in `~/go/pkg/mod/github.com/charmbracelet/x/exp/golden@v0.1.0/testdata/`.
  If a future AGY alignment wants them to be human-readable (e.g. hex
  escaped), that's a one-line wrapper change.
- `go.mod` correctness: `go mod tidy` reclassified
  `charmbracelet/ultraviolet`, `charmbracelet/x/term`, and
  `muesli/cancelreader` from direct to indirect. Confirmed these are
  not directly imported anywhere in the tree
  (`grep -rn 'charmbracelet/ultraviolet"|charmbracelet/x/term"|muesli/cancelreader"' --include='*.go'`
  returned zero matches; the only mentions of these names in the tree
  are in comments). The reclassification is correct, but it is a
  tangential side effect of `go mod tidy` that wasn't strictly
  required by the cycle brief.
- Pre-existing test flakes (`TestDispatchPrintSlash_LocalCommands`,
  and the other 6 in the parent brief's list) continue to be unaffected
  by this cycle. `TestDispatchPrintSlash_LocalCommands` fails on this
  run as expected; the other 6 pass.
- File mode of golden files is `0600` because `os.WriteFile` from
  the `golden` package uses that bit. Untracked files in git get
  their executable bit from the umask (default 0644 for new files
  ignoring go's write); on commit they'll land in the tree with the
  standard mode.
